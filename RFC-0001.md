- **Title**: Amoeba Storage Architecture & Ingestion Protocol (AmoebaBelly)

- **Last Updated**: 2026-09-13
- **Target Implementation**: Go 1.27 (`local/AmoebaStorage`)

---

## 1. Abstract

Amoeba Storage is a high-performance, single-celled object storage engine and line-rate content delivery network (CDN) written in pure Go from first principles. Drawing foundational architectural inspiration from Bitcask (append-only write log + in-memory hash table) and Facebook Haystack (multi-blob volume striping, physical/logical separation, guaranteed single-disk-seek reads), Amoeba treats binary objects as raw, opaque blobs.

This RFC standardizes the internal storage engine architecture, physical disk layout ("Amoeba Belly"), streaming ingestion pipeline with real-time integrity verification, metadata journaling format, lock contention model, and the federated multi-cluster edge distribution roadmap.

---

## 2. Conventions & Terminology

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **MAY**, and **OPTIONAL** in this document are to be interpreted as described in BCP 14 [RFC 2119].

- **Organism (Engine)**: The low-level Go storage engine managing volumes, byte ingestion, index state, and disk controllers.
- **The Belly**: The validated physical root storage directory on the host filesystem.
- **The Heap (Volumes)**: Species-named directories storing raw, immutable blob payloads.
- **The Stack (Metadata)**: The durable append-only metadata catalog storing `.meta` journal entries.
- **The Guard**: The edge HTTP/CDN service handling authentication, rate limiting, and transport framing.
- **The Librarian**: The internal engine core strictly isolated from transport protocols.

## 3. Core Architectural Dogma

### 3.1 Separation of Concerns: The Librarian vs. The Guard
The system MUST maintain strict structural decoupling between transport networking and disk controllers:

```
┌───────────────────────────────────────────────────────────────┐
│                    THE GUARD (HTTP / CDN Edge)                 │
│  - Line-rate GET / POST handling     - Token-based Auth (JWT) │
│  - ETag / If-None-Match 304 Caching  - Range Requests (RFC9110)│
└───────────────────────────────┬───────────────────────────────┘
                                │ Transport-agnostic Go API (io.Reader)
┌───────────────────────────────▼───────────────────────────────┐
│                 THE LIBRARIAN (Storage Engine)                │
│  - AmoebaBelly anatomy validator     - Round-robin allocator  │
│  - Single-pass streaming ingestion   - CRC32C Castagnoli hash │
│  - Append-only metadata journal      - In-memory hash index   │
└───────────────────────────────────────────────────────────────┘
```

The storage engine MUST NOT depend on `net/http` primitives, headers, bearer tokens, or transport encodings. It operates purely on `(key string, size int64, stream io.Reader, expectedCRC uint32)`.

### 3.2 Memory Safety & Line of Sight
All engine implementations MUST adhere to left-margin line-of-sight Go idioms:
- Guard clauses with immediate returns (`if err != nil { return ..., err }`).
- Zero `else` branching following error checks.
- Bounded memory allocations ($O(1)$ streaming scratchpad buffers). Whole-file RAM buffering is strictly FORBIDDEN.

## 4. Physical Disk Anatomy ("Amoeba Belly")

### 4.1 Belly Layout
The engine root directory MUST conform to the following hierarchy:

```
<DataDir>/
├── .amoeba                       ◄── Ownership marker file
├── metadata/                     ◄── The Stack (Control Plane)
│   ├── stack.<UUID-1>.meta
│   ├── stack.<UUID-2>.meta
│   └── ...
└── volumes/                      ◄── The Heap (Data Plane)
    ├── proteus/                  ◄── Virtual Volume 0
    │   └── <UUID-A>
    ├── dubia/                    ◄── Virtual Volume 1
    │   └── <UUID-B>
    ├── chaos/                    ◄── Virtual Volume 2
    ├── radiosa/
    ├── discoides/
    ├── vespertilio/
    ├── terricola/
    └── limax/
```

### 4.2 Marker Verification & Collision Defense
To prevent catastrophic accidental mounting over foreign host directories, the initialization routine (`AmoebaBelly`) MUST execute the following validation algorithm on startup:

1. `os.Stat(absRoot)`:
   - If `os.IsNotExist`: Execute `os.MkdirAll(absRoot, 0755)`.
   - If path exists and `!info.IsDir()`: MUST return `ErrInvalidDirectory`.
2. Directory contents inspection:
   - Read all entries via `os.ReadDir(absRoot)`.
   - Filter out OS metadata files (`.DS_Store`, `.gitkeep`).
   - If real file entries exist and `.amoeba` marker is absent: MUST immediately abort with `ErrDirectoryPolluted`.
3. Marker claim: Touch `.amoeba` via `os.OpenFile(..., os.O_CREATE|os.O_WRONLY, 0644)`.
4. Subdirectory provisioning: Ensure `metadata/` and `volumes/` exist.
5. Species provisioning: Initialize $V$ virtual volume folders cycling through `SpeciesRoster`.

### 4.3 Production Physical Mount Mapping
While virtual volumes initially share a single root mount during single-node prototyping, the engine architecture MUST support binding species directories to discrete block device mounts (`/mnt/disk_{n}/<species>`) with zero modifications to engine call sites.

### 4.4 2-Tier SHA-256 Directory Sharding
When storing millions of objects per species volume, flat directories cause severe filesystem performance degradation due to ext4/xfs directory block linear scans.
- The engine MUST support optional 2-tier directory sharding via the `--enable-sharding` configuration flag.
- When enabled, target object paths derive from the first 4 hex characters of the object ID:
  ```
  volumes/<species>/<hex[0:2]>/<hex[2:4]>/<objectID>
  # Example: volumes/proteus/e4/a3/e4a3b8d91f0c2e3a4b5c6d7e8f901234
  ```
- Sub-tier sharding directories are provisioned on demand with permissions `0755`.
- In-memory index keys remain flat (`<species>/<objectID>`); path resolution translates internal storage tiers transparently.

## 5. Ingestion Pipeline & Data Plane Mechanics

### 5.1 Ingestion Flow
Object ingestion MUST follow a single-pass streaming architecture:

```
Client HTTP Request
        │
        ▼ (io.Reader stream)
[ Ingest(key, size, stream, expectedCRC) ]
        │
        ├── 1. Assign Target Volume (Round-robin striping under volMu.Lock)
        │
        ├── 2. eatObject()
        │       ├── Generate UUID (16 cryptorandom bytes -> hex)
        │       ├── Create target file: volumes/<species>/<UUID>
        │       ├── Stream pipe: io.MultiWriter(diskFile, crc32.New(Castagnoli))
        │       ├── Copy loop: io.CopyBuffer() with 32 KB scratchpad
        │       ├── Flush: diskFile.Sync()
        │       └── Integrity gate: Validate written == size && crc == expectedCRC
        │           └─ FAIL: os.Remove(targetFile) + revert volume quota -> return err
        │
        └── 3. registerObject()
                ├── Serialize MetadataEntry JSON
                ├── Durable journal write: stack.<UUID>.meta (with retries)
                └── Atomic commit: index[key] = entry (under metaMu.Lock)
```

### 5.2 Zero-Staging Direct Disk Streaming (`eatObject`)
- Storage engines MUST NOT stage writes into intermediate temporary directories or RAM buffers.
- Streams MUST be written directly to their destination path `volumes/<species>/<objectID>` using a fixed 32 KB scratchpad buffer (`defaultStreamBufferSize = 32 * 1024`).
- Memory footprint during streaming write is strictly bounded: $O(1)$ memory overhead ($32\text{ KB}$) independent of whether the object is $1\text{ MB}$ or $100\text{ GB}$.

### 5.3 On-the-Fly Castagnoli Integrity Verification
- Integrity hashing MUST be computed concurrently with the disk write pass using an `io.MultiWriter` wrapping the file descriptor and a `crc32.Hash32` instance using the Castagnoli polynomial table (`0x82F63B78`).
- Post-write verification gates:
  1. `written == size`: Prevents truncated network streams (`ErrSizeMismatch`).
  2. `computedCRC == expectedCRC` (when `expectedCRC != 0`): Prevents bit rot and payload corruption in transit (`ErrChecksumMismatch`).
- If any check fails, the uncommitted file MUST be deleted immediately via `os.Remove`, and volume capacity reservations MUST be credited back.

### 5.4 Conveyor Belt Worker Pipeline (`objRefStreamBufChan`)
To achieve non-blocking ingestion concurrency under high throughput ($C100K$ scale), the ingestion architecture supports decoupling the HTTP transport worker from the physical disk writer via a bounded Go channel conveyor belt:

```
HTTP Handler (Worker)
        │
        ├── 1. Assigns target volume species
        ├── 2. Allocates private Done channel: make(chan UploadResult, 1)
        ├── 3. Enqueues UploadTask onto objRefStreamBufChan (buffer: 128)
        │
        ├── [ Waits on task.Done channel ] ◄──────────┐
        │                                              │ Signals Result
        ▼ (Piped stream reference)                     │ (Address / Err)
┌──────────────────────────────────────────────────────┴────────┐
│ Uploader Daemon Pool (eatObject + registerObject)             │
│ - Pulls tasks from objRefStreamBufChan                        │
│ - Increments / decrements sync.WaitGroup (e.wg)               │
│ - Performs disk sync, CRC verification, and metadata write    │
└───────────────────────────────────────────────────────────────┘
```
- **Stream Reference Ownership**: The channel conveys an `io.Reader` interface pointer (`task.Stream`). Bytes are read directly from the network socket without duplicating memory in userspace.
- **Shock Absorption**: The channel buffer depth (default `128`) absorbs bursty traffic spikes without stalling HTTP connection acceptance.
- **Private Done Channel Signaling**: Each `UploadTask` provisions its own dedicated `Done chan UploadResult`. The uploader communicates success/failure back to the originating HTTP handler thread safely without global lock contention.
- **Graceful Shutdown**: The engine tracks active uploader tasks via `sync.WaitGroup`. On SIGINT/SIGTERM, the server stops accepting new uploads, drains `objRefStreamBufChan`, and waits for in-flight writes to sync to disk before terminating.

### 5.5 Tunable Scratchpad Knobs (Ghost Configurations)
The engine defines staged ghost configuration parameters allowing runtime tuning of I/O performance:
- `StreamBufferSize`: Scratchpad buffer size for `io.CopyBuffer` (default 32 KB; tunable to 64 KB or 128 KB for high-bandwidth NVMe pipelines).
- `CleanUpCycleWindow`: Periodic GC duration (default 48 hours).
- `VirtualVolumesCap` and `VirtualVolumeSizeCap`: Provisioning ceilings for species volumes.

## 6. Control Plane & Metadata Journaling

### 6.1 Metadata Schema (`stack.<UUID>.meta`)
Every stored object is permanently recorded in a dedicated JSON manifest in `metadata/stack.<objectID>.meta`:

```json
{
  "id": "e4a3b8d91f0c2e3a4b5c6d7e8f901234",
  "key": "users/avatars/u_1092.png",
  "object_pointer": "proteus/e4a3b8d91f0c2e3a4b5c6d7e8f901234",
  "file_size": 245912,
  "checksum_crc32": 3948572102,
  "replica_id": 0,
  "auto_cleanup": false,
  "integrity_verified": true,
  "lock_status": false,
  "created_at": "2026-09-04T15:45:00.123456Z"
}
```

### 6.2 Durability & Retry Backoff
The metadata journal writer (`registerObject`) MUST guarantee on-disk durability:
1. File descriptor opened with `os.O_CREATE | os.O_WRONLY | os.O_TRUNC`.
2. Serialized payload written and flushed with explicit `metaFile.Sync()`.
3. Transient failures (e.g. storage I/O stalls) MUST trigger retry backoff up to `RetriesLimit` (default `3`):
   $$\text{sleep} = \text{attempt} \times 25\text{ ms}$$
4. Upon successful sync, pointer `index[key]` is committed to the in-memory index map under `metaMu.Lock()`.

### 6.3 Point Lookups ($O(1)$ Disk Seek)
Point read requests query `index[key]`:
- Resolves `object_pointer` (`<species>/<objectID>`) instantly from RAM.
- Reads direct file offset: exactly **1 disk seek** to reach the byte payload.

### 6.4 Sparse Indexing & Fixed Hot Object Buffer
To prevent RAM exhaustion when cataloging tens of millions of objects:
- **Sparse RAM Index**: The primary in-memory index MUST store only minimal resolution keys (`Key -> (ObjectPointer, FileSize, CRC32)`), stripping auxiliary verbose metadata from long-lived RAM.
- **Fixed-Capacity In-Memory Hot Buffer**: An optional bounded LRU buffer caches frequently accessed hot objects directly in memory. If memory limits are reached, cold objects are evicted immediately without writeback penalties (since disk storage is immutable and append-only).

### 6.5 Compaction & Periodic Compressed Hintfile Backups
Continuous writes generate numerous individual `stack.<UUID>.meta` journal files, eventually increasing directory inode counts:
- The engine MUST support periodic background metadata compaction.
- The compactor walks active `stack.*.meta` files, discards records marked with deletion tombstones, and writes a consolidated, gzip-compressed hintfile (`stack.compact.gz`).
- Critical-path live writes bypass compression/decompression entirely to avoid CPU contention.

## 7. Concurrency, Striping & Lock Mechanics

### 7.1 Round-Robin Striping Allocator (`assignVol`)
Volume assignment balances write loads evenly across all active species volumes:

```go
currVolIdx := e.volumeidx
for nextIdx := 0; nextIdx < totalVol; nextIdx++ {
    destinationVolIdx := (currVolIdx + uint64(nextIdx)) % uint64(totalVol)
    vol := e.volume[destinationVolIdx]
    if vol.IsFull || (vol.UsedBytes+size > vol.MaxBytes) {
        continue
    }
    vol.UsedBytes += size
    if vol.UsedBytes >= vol.MaxBytes {
        vol.IsFull = true
    }
    e.volumeidx = (destinationVolIdx + 1) % uint64(totalVol)
    return vol, nil
}
```

### 7.2 Fine-Grained Object-Level Locking
- Engines MUST NOT acquire volume-wide locks during object deletion, read, or metadata update.
- Modifying operations MUST set `MetadataEntry.LockStatus = true` on the targeted object entry.
- Concurrent reads on an object with `LockStatus == true` MUST return `ErrObjectLocked` until the lock is released or tombstoned.

## 8. Ephemeral Lifecycle & Garbage Collection

### 8.1 The `Autokill` Mechanism
Objects generated for transient operations (e.g., job applicant resumes before final form submission, processing scratchpads, media transcoding buffers) MAY be flagged with `Autokill = true`.

### 8.2 Background Cleanup Daemon
The storage engine maintains a background sweeper running every `CleanUpCycleWindow` (default 48 hours):
1. Scans metadata stack entries where `Autokill == true`.
2. If `time.Since(CreatedAt) > EphemeralTTL`:
   - Mark `LockStatus = true`.
   - Remove physical blob from `volumes/<species>/<objectID>`.
   - Remove metadata journal `metadata/stack.<objectID>.meta`.
   - Evict key from in-memory index.
   - Reclaim volume quota `vol.UsedBytes -= size`.

### 9.1 Multi-Cluster Peer-to-Peer Replication Protocol
Amoeba implements a synchronous multi-cluster replication protocol enabling independent clusters to serve identical objects transparently.

```
Client Write Request
         │
         ▼
┌───────────────────┐
│ Primary Node      │
│ (ReplicaID: 0)    │
└────┬─────────┬────┘
     │         │ Synchronous Forwarding (HTTP/TLS Stream)
     │         ├───────────────────────────────┐
     ▼         ▼                               ▼
 Local Disk  ┌───────────────────┐   ┌───────────────────┐
  Ingestion  │ Replica Node 1    │   │ Replica Node 2    │
             │ (ReplicaID: 1)    │   │ (ReplicaID: 2)    │
             └─────────┬─────────┘   └─────────┬─────────┘
                       │ Acknowledgment        │ Acknowledgment
                       └───────────────┬───────┘
                                       ▼
                       Quorum Commit (IntegrityVerified = true)
```

#### 9.1.1 Replica Identity & Tracking (`ReplicaID`)
- Every physical object copy is tagged in its `MetadataEntry` with an explicit `ReplicaID` (int):
  - `ReplicaID = 0`: Primary ingestion origin.
  - `ReplicaID >= 1`: Downstream replica rank within the placement group.
- `ChecksumCRC32` MUST match identically across all replicas. The Castagnoli CRC32C serves as the universal cross-cluster fingerprint for replica validation and collision rejection.

#### 9.1.2 Synchronous Write Pipeline
1. Primary node receives stream from client and initiates local `eatObject`.
2. Concurrently, Primary pipes the stream via `io.TeeReader` to target replica clusters resolved via Kubernetes API topology.
3. Each replica node streams bytes directly into its local species volume (`volumes/<species>/<UUID>`), computing CRC32C in real time.
4. Quorum gate: Primary waits for synchronous write acknowledgments from $W$ replicas ($W \ge \lfloor R/2 \rfloor + 1$ where $R$ is replication factor) before committing `IntegrityVerified = true` to its metadata stack and returning success to client.
5. If replica quorum fails, rollback occurs across nodes, cleaning up partially written blobs.

#### 9.1.3 Synchronous Read Load Balancing
- Read requests MAY hit any cluster in the federation.
- If the receiving node contains a local replica (`ReplicaID >= 0` with `IntegrityVerified == true`), it serves the object directly with guaranteed $O(1)$ disk seek.
- If the node does not host the physical replica, it inspects its cached nearest-neighbor metadata (`cluster_id/stack_<UUID>.meta`), and either:
  - Streams the payload as an edge reverse-proxy, or
  - Returns an HTTP `307 Temporary Redirect` pointing the client directly to the closest healthy replica node.

#### 9.1.4 Cross-Cluster Self-Healing & Active Anti-Entropy
A background daemon runs continuously to guarantee replica durability:
1. Compares metadata digests with nearest peer clusters discovered via Kubernetes API.
2. If a node detects a missing replica or degraded node from the binary `HeartBeat` flags, it schedules an asynchronous replication pull.
3. The recovering node pulls the raw stream from a healthy peer, verifies `ChecksumCRC32`, and writes its local volume and metadata stack.

### 9.2 $N/2$ Nearest-Neighbor Metadata Partitioning
To prevent $O(N)$ RAM explosion in large multi-cluster deployments:
- A node MUST NOT cache metadata from all clusters in the global fleet.
- A local background latency daemon computes network round-trip distances between clusters.
- Each node caches metadata journals from only its nearest $\lfloor N/2 \rfloor$ neighbor clusters.
- Distant queries are forwarded dynamically over internal cluster gateway routes.

### 9.3 Custom Binary Telemetry & Diagnostic Study (`HeartBeat`)
Inter-node cluster health probing and runtime telemetry run over a custom low-latency binary socket instead of verbose HTTP:
- **Frame Wire Layout**:
  ```
  Byte 0: [ MAGIC 0xAB ]
  Byte 1: [ PROTOCOL_VER: 4 bits | NODE_STATUS: 4 bits ]
  Byte 2: [ STORAGE_LOAD_PCT: 8 bits (Used / Total * 100) ]
  Byte 3: [ FLAGS: IsFull(bit 0) | ShardingEnabled(bit 1) | Degraded(bit 2) | EphemeralActive(bit 3) ]
  Bytes 4-7: [ CRC32C of header payload ]
  ```
- **Diagnostic Study Probing**: The socket accepts diagnostic probe queries requesting real-time telemetry metrics without HTTP overhead:
  - `CMD_STUDY_IOPS`: Real-time ingestion write rate and disk sync latency.
  - `CMD_STUDY_VOLUMES`: Per-species volume capacities and fragmentation indices.
  - `CMD_STUDY_REPLICAS`: Cross-cluster peer replication lag and checksum consistency scores.

## 10. Edge CDN Delivery Mechanics (The Guard)

Amoeba's HTTP interface serves as an integrated, line-rate Content Delivery Network edge origin:

### 10.1 Kernel Zero-Copy Egress (`sendfile(2)`)
For blob retrieval requests (`GET /objects/{key}`):
- Linux environments MUST leverage zero-copy syscalls (`sendfile(2)` or `splice(2)`).
- Bytes transfer directly from the volume file descriptor into the TCP network socket within kernel space, avoiding context switches and eliminating userspace heap allocations.

### 10.2 Natural ETag Caching (`304 Not Modified`)
- The precomputed `MetadataEntry.ChecksumCRC32` serves directly as the HTTP `ETag` header (e.g., `ETag: "w/e4a3b8d9"`).
- On requests carrying `If-None-Match`, the Guard verifies the hash directly against the in-memory index.
- If hashes match, the Guard responds with `HTTP 304 Not Modified` with **zero disk reads**, saving 100% of I/O bandwidth.

### 10.3 RFC 9110 Byte-Range Requests (`206 Partial Content`)
- To support video streaming, audio scrubbing, and resumable downloads, the Guard implements HTTP range requests according to RFC 9110 / RFC 7233.
- Parsing `Range: bytes=start-end` translates into an explicit `os.File.Seek(start, io.SeekStart)` and `io.CopyN` for the requested segment, returning `HTTP 206 Partial Content`.

## 11. Security & Threat Modeling

1. **Path Traversal Attacks**: All incoming keys and volume targets are sanitized via `filepath.Abs` and verified to reside strictly within `Belly` subtrees. Traversal sequences (`../`) MUST yield `ErrPathEscaped`.
2. **Resource Exhaustion**: Direct streaming writes with non-zero size checks prevent zero-byte spam (`ErrInvalidPayloadSize`) and payload overages.
3. **Foreign Data Integrity**: The `.amoeba` marker prevents the engine from mounting arbitrary host paths and overwriting user data.
4. **Transport Security**: The Guard edge MUST enforce TLS termination and cryptographically signed token verification (JWT/PASETO) before passing requests to the Librarian.
